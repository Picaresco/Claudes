# ClaudHome

![ClaudHome: tus sesiones de Claude Code, en casa](docs/cabecera.jpg)

Sesiones de Claude Code en pestañas: cada pestaña es un `claude` trabajando en su carpeta, con el nombre que tú le pongas.

Proyecto personal para Windows. No está afiliado a Anthropic ni a OpenAI.

Antes se llamaba Claudes. Solo ha cambiado el nombre que se ve: el ejecutable (`Claudes.exe`), el repositorio y las carpetas de la app conservan el nombre anterior, para que las instalaciones existentes sigan funcionando y actualizándose.

## Requisitos

- Windows 10 u 11.
- [Claude Code](https://code.claude.com/docs) instalado y con sesión iniciada (`claude` en el PATH).
- Opcional: Git para Windows (trae Git Bash), para que Claude explique lo que hace.
- Opcional: Codex CLI con sesión de ChatGPT, para que Claude pueda pedirle segundas opiniones, revisiones e imágenes.
- Solo para ejecutar desde el código o generar el ejecutable: Node.js 22.13 o posterior, salvo la 23 (lo pide ESLint). Para usar la app y actualizarla no hace falta.

## Instalación

Descarga `ClaudHome-win32-x64.zip` de la [última versión publicada](https://github.com/Picaresco/Claudes/releases/latest), descomprímelo en una carpeta tuya (por ejemplo `%LOCALAPPDATA%\Programs`) y abre `Claudes-win32-x64\Claudes.exe`. A partir de ahí se actualiza sola con el botón «Actualizar».

Para ejecutarla desde el código:

```
git clone https://github.com/Picaresco/Claudes.git
cd Claudes
npm install
npm start
```

La primera vez, `npm start` descarga el binario de Electron. Para tener un ejecutable que abrir sin terminal, `npm run package` genera `dist\Claudes-win32-x64\Claudes.exe`.

## Qué hace

- **Pestañas con nombre y color.** Doble clic o `F2` para renombrar; clic derecho para sus opciones (color, cerrar…); se reordenan arrastrándolas por la fila. Se cierran desde esas opciones, con `Ctrl+Mayús+W` o con el botón central del ratón.
- **Pegar imágenes y documentos.** `Ctrl+V` o botón derecho pegan lo que haya en el portapapeles: texto, archivos copiados en el Explorador (se pegan sus rutas; Claude adjunta las imágenes como `[Image #1]`) o una imagen copiada, como una captura de pantalla. También se pueden soltar archivos sobre la terminal.
- **Contexto del proyecto.** Con el botón «Contexto» de cada pestaña se abre un panel con una nota para Claude y una lista de documentos (PDF, Word, imágenes, textos), carpetas y enlaces web que Claude tiene presentes en todas las sesiones de esa pestaña. Se añaden de tres formas: con los botones del panel («Añadir enlace…» para las páginas web), arrastrándolos al panel (también enlaces desde el navegador), o soltándolos sobre la sesión y eligiendo «Añadir al contexto del proyecto». Claude no los lee por adelantado: los abre cuando la tarea los necesita, sin pedir permiso. De cada enlace se muestra el título de la página. Si la página pide iniciar sesión, la tarjeta avisa de que Claude no podrá leerla; en ese caso, guárdala como PDF y añade el PDF. Cada documento se puede desactivar o quitar, y «Ver lo que recibe Claude» muestra el texto exacto que se le pasa. No se toca ningún archivo del proyecto.
- **Vista previa al pasar el ratón.** Sobre el `[Image #n]` de una imagen pegada, o sobre la ruta de cualquier archivo que exista (la que pegues tú o la que escriba Claude en su respuesta), aparece una tarjeta con la vista previa: la miniatura de una imagen, la primera página de un PDF, las primeras líneas de un archivo de texto o código, y para lo demás la miniatura de Windows o el icono de su tipo. Debajo salen el tipo, el tamaño, y las dimensiones o páginas. `Ctrl`+clic abre el archivo.
- **Cierre ordenado.** Al cerrar una pestaña (o la app) con Claude trabajando, avisa. «Guardar estado y cerrar» interrumpe la tarea, le pide a Claude que deje anotado por dónde iba y espera a que termine antes de cerrar; al reabrir la sesión, ese resumen es lo último de la conversación. «Cerrar ya» corta en el acto.
- **Registro de depuración.** Activado de serie; se apaga y enciende con el botón «Depuración» de la barra inferior. Los registros quedan en la carpeta `logs` de los datos de la app (`%APPDATA%\Claudes\logs`).
- **Actualizaciones desde GitHub.** Si en GitHub hay una versión mayor que la instalada, aparece el botón «Actualizar a vX.Y.Z» en la barra superior. Al pulsarlo se muestran los cambios de todas las versiones posteriores a la tuya, agrupados por versión. Con «Cancel» no se toca nada: actualizar no es obligatorio y el botón sigue ahí. Con «Update», ClaudHome descarga la versión nueva ya preparada (unos 160 MB), comprueba que ha llegado entera y que haya un acceso directo en el escritorio (si falta, lo crea). No hace falta tener nada más instalado. Todo esto ocurre en segundo plano, el botón va mostrando el avance y puedes seguir trabajando. Al terminar, ClaudHome se reinicia para instalarla; si alguna sesión está trabajando, pregunta antes de cerrar. Al volver se abren tus pestañas y cada sesión retoma su conversación. La versión que ya tenías queda guardada como copia.
- **Dictado por voz.** El micrófono de la barra superior activa el dictado de Claude Code: amarillo oscuro = activado, gris oscuro = desactivado. Activado, mantén pulsada la barra espaciadora en una sesión para hablar; al soltarla deja de grabar y el texto queda en el cuadro de Claude para revisarlo y enviarlo con `Intro`. Desactivado, la barra espaciadora solo escribe espacios. Vale al momento para todas las pestañas. Necesita una sesión de Claude Code iniciada con cuenta de Claude.ai y permiso de micrófono para las aplicaciones de escritorio en Windows.
- **Imágenes con Codex.** El indicador de la barra superior muestra si Codex está instalado con una suscripción de ChatGPT. Al activarlo, las sesiones de Claude reciben la herramienta `generar_imagen`, que pide la imagen a Codex y la guarda en la carpeta de la sesión.
- **Estado de cada sesión.** El punto de cada pestaña lo indica:
  - aro verde girando: trabajando;
  - punto verde: activa, esperando tu mensaje;
  - punto rojo parpadeando: te necesita (pide permiso o una respuesta);
  - punto verde parpadeando: ha terminado sin que lo vieras;
  - punto ámbar: se ha detenido por un error (fallo de la API, límite de uso…), hasta tu siguiente mensaje;
  - aro gris girando: arrancando o guardando su estado para cerrar;
  - círculo punteado: sin iniciar, dormida o sesión cerrada.
  
  Si no estás mirando esa pestaña, salta además una notificación de Windows. La barra inferior cuenta cuántas sesiones hay en cada caso.
- **Sesiones dormidas.** Una sesión que lleva 45 minutos esperando tu mensaje en una pestaña que no estás viendo se duerme: se cierra para liberar memoria (cada sesión, con sus servidores MCP, ocupa en torno a 1 GB). La conversación queda guardada y se retoma sola al abrir la pestaña. Nunca se duerme una sesión que está trabajando, que te necesita, que ha terminado sin que lo vieras, que tiene un error o que ha dejado algo en marcha (una tarea en segundo plano, una vigilancia o una tarea programada).
- **Llenado de la conversación.** Una barrita al pie de cada pestaña muestra cuánto de su ventana de contexto ocupa la conversación: verde hasta el 60 %, ámbar hasta el 85 % y coral a partir de ahí. Al pasar el ratón por la pestaña se ve el porcentaje y los tokens que lleva usados la conversación (incluidos los de sus subagentes), con su desglose. Cuanto más llena, peor rinde Claude y más gasta: `/compact` la resume y sigue, `/clear` empieza de cero.
- **Tarjeta del proyecto (botón derecho sobre una pestaña).** Reúne lo de esa pestaña: su nombre, carpeta y estado; un botón de compartir que copia la dirección del proyecto en GitHub (`https://github.com/dueño/repositorio`, construida de nuevo a partir del remoto de git, sin usuario ni clave; si no hay remoto de github.com, el botón queda apagado); cuánto ocupa la conversación y lo gastado en ella; el modelo y el esfuerzo; el autocompactar, y las acciones de siempre (cambiar nombre, color —nueve para elegir—, nueva conversación, abrir la carpeta y cerrar la pestaña).
- **Modelo y esfuerzo.** La barra inferior dice el modelo y el esfuerzo de razonamiento de la pestaña que estás viendo («Opus 5.5 · esfuerzo muy alto»); solo informa. Se cambian en la tarjeta del proyecto: Opus, Sonnet, Haiku o Fable, y el esfuerzo de bajo a máximo. Se aplica con «Aplicar», reiniciando la sesión de esa pestaña, que sigue con la misma conversación, y la pestaña lo recuerda. Solo cambia esa pestaña, salvo que marques «Usar también en las sesiones nuevas», que lo guarda como predeterminado de Claude Code (lo mismo que hacen `/model` y `/effort` dentro de una sesión). Si Claude está trabajando, se aplica cuando termine.
- **Autocompactar.** Al llegar la conversación a un porcentaje de su contexto, Claude Code la resume sola y sigue. De serie, el 85 % en todos los proyectos; en la tarjeta del proyecto se elige otro para cada pestaña (del 30 al 95 %, con un deslizador y los valores rápidos 50, 70, 85 y 95). Más bajo gasta menos del límite semanal, porque cada mensaje lleva menos historia; más alto, Claude recuerda más detalle. Claude Code lo lee al arrancar (`CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`): un cambio en una pestaña abierta se aplica con «Aplicar», en el mismo reinicio que el modelo. Si ya tienes esa variable puesta, manda la tuya.
- **Límite de uso y tokens.** La barra inferior muestra el gasto semanal de tu plan de Claude en un recuadro terracota, con su barra, su porcentaje y cuándo se renueva («Claude ▬▬ 61 % · se renueva hoy a las 21:00»); el de Codex va al lado, en verde agua. Cerca del límite, el porcentaje pasa a ámbar y, muy cerca, a rojo con «⚠». Si tu plan tiene además límite de 5 horas, se añade su porcentaje. Al pasar el ratón se ven los tokens usados en la semana y su desglose: entrada, salida, caché escrita y caché leída. El porcentaje del límite es el de tu cuenta, incluido lo usado en claude.ai o en otros equipos; los tokens son los de Claude Code en este equipo. Con una clave de API no hay límites del plan: la barra no aparece.
- **Rueda de opciones.** El botón con forma de rueda de la barra superior abre un panel con todos los interruptores: Resumido, Codex asesora, imágenes con Codex, micrófono y depuración. Abajo está el «Log», con el número de entradas del proyecto. Cada uno lleva una línea que explica para qué sirve; pulsarlos no cierra el panel, que se cierra al pulsar fuera o con Esc. Mientras Codex trabaja, lo dice el indicador de al lado. Cada petición a Codex se ve volar desde la terminal hasta el indicador, y su respuesta de vuelta (`ui/codex-flight.js`; no con el mapa del «Workflow» ni con las animaciones de Windows desactivadas).
- **Indicador de Codex.** Junto a la rueda, el nombre «Codex» dice de un vistazo cómo está: verde si se ha detectado en el equipo con tu cuenta de ChatGPT, gris si no está instalado y ámbar si está instalado pero sin sesión (o con clave de API). Mientras trabaja lleva al lado un icono animado por cada cosa que hace, con el tiempo que lleva: el símbolo de código (revisa lo que ha cambiado Claude), una lista que se va marcando (critica un plan), un bocadillo (da una segunda opinión; un escudo si es de seguridad) o un pincel pintando (genera una imagen); al pasar el ratón dice para qué proyecto y en qué (una segunda opinión, la crítica de un plan o una revisión). Si se acerca a su límite de uso (80 % o más), el nombre pasa a ámbar con el porcentaje, y a rojo si lo agota. Al pulsarlo abre las opciones; si Codex no se puede usar, lo vuelve a comprobar.
- **Hasta 6 proyectos abiertos.** Para no saturar la barra superior, se pueden tener 6 pestañas a la vez. Al intentar abrir otra (nueva o desde Recientes), ClaudHome avisa de que hay que cerrar alguna; la que se cierra queda en Recientes con su conversación. Si ya tenías más de 6 guardadas, se respetan al abrir la app.
- **Barra inferior en una línea.** El uso de Claude, el de Codex y el de la conversación caben siempre en una línea: si falta sitio, la barra se compacta por pasos (sin la pista de atajos, con las fechas abreviadas, sin los tokens, solo los porcentajes y, al final, sin el recuento de sesiones ni las barritas y recortando la parte izquierda) y vuelve a mostrarlo todo al ensanchar la ventana. El detalle completo está al pasar el ratón.
- **Codex en la barra inferior.** Junto al uso de Claude, la barra inferior dice si hay Codex en este equipo y, con tu cuenta de ChatGPT, el porcentaje gastado de su límite semanal y cuándo se renueva. Incluye lo que uses de Codex fuera de ClaudHome. Se actualiza al abrir la app, cada 10 minutos y tras cada consulta a Codex, sin gastar nada.
- **Codex como asesor de Claude.** Si tienes [Codex](https://github.com/openai/codex) instalado y con tu cuenta de ChatGPT, Claude puede pedirle una segunda opinión con su modelo más capaz cuando se enfrenta a una decisión importante (arquitectura, el enfoque de una tarea grande, cambios de seguridad o de infraestructura) o a un problema que no le sale. También puedes pedírsela tú: «pide una segunda opinión a Codex». Codex lee el proyecto en solo lectura, sin cambiar nada; Claude compara su análisis con el suyo y te da una sola recomendación, señalando en qué coinciden y en qué no. Cada consulta tarda entre medio minuto y unos minutos, gasta de tu plan de ChatGPT y queda en el «Log». Todo lo de Codex como asesor (segunda opinión, crítica de planes y revisión del código) depende del interruptor «Codex asesora», que viene apagado: lo enciendes si quieres usar Codex. Apagado, Claude no le consulta nada.
- **Codex como segundo revisor.** Con el interruptor «Codex asesora» encendido, Codex critica el plan que Claude presenta en modo planificación (Mayús+Tab) antes de que lo veas; fuera de ese modo, Claude le pide una segunda opinión sobre sus planes para tareas grandes antes de empezar (Claude lo ajusta y te lo presenta con una sección «Segunda opinión (Codex)»), y cuando Claude termina un turno en el que ha cambiado código, Codex revisa todos los cambios sin confirmar del proyecto (también los tuyos) con su modelo más capaz, en solo lectura, razonando lo que haga falta (más a fondo en cambios de seguridad, despliegue o datos y en cambios grandes). Si encuentra algo, Claude lo evalúa, corrige lo que sea un fallo real y te cuenta qué ha hecho; lo que no ha tocado él, te lo comenta sin cambiarlo. Una sola ronda por turno, solo en los turnos empezados con el interruptor encendido, solo en proyectos con git y nunca en el turno de cerrar la sesión. Añade entre medio minuto y unos minutos por turno y gasta de tu plan de ChatGPT (nunca una clave de API). Lo revisado sale hacia OpenAI y queda en el «Log»; si lo que se iba a enviar lleva una clave, no se revisa. Como Claude, Codex puede abrir otros archivos del proyecto para entender los cambios.
- **Respuestas con explicaciones o resumidas.** De serie, Claude explica lo que hace con el plugin [explanatory-output-style](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/explanatory-output-style) de Anthropic: mientras trabaja, añade bloques «★ Insight» con el porqué de sus decisiones y lo que va viendo del proyecto. El interruptor «Resumido» de la barra superior cambia a respuestas cortas y al grano, y al apagarlo vuelven las explicaciones. Vale para todas las pestañas desde tu siguiente mensaje, sin reiniciar nada. Las explicaciones gastan algo más de tokens.
- **Diseño con personalidad.** La app trae el plugin [frontend-design](https://github.com/anthropics/claude-plugins-official/tree/main/plugins/frontend-design) de Anthropic, el más instalado de Claude Code. Cuando pides una web, una app o una pantalla, Claude lo usa solo: elige colores, tipografía y estructura pensados para lo que estás haciendo, en vez del aspecto genérico de una plantilla. No hay nada que activar.
- **Pruebas antes de terminar.** Otra buena práctica para cualquier proyecto: si Claude cambia código y el proyecto tiene pruebas, antes de terminar el turno se le pide que las pase si no lo ha hecho después de su último cambio. Si fallan por su cambio, lo corrige; si fallan por otra cosa, te lo cuenta; si su cambio no puede afectar a nada de lo que prueban, lo dice y termina. Y «ha terminado» no esconde unas pruebas que fallan: si fallan y Claude va a terminar, se le pide una vez que lo corrija o que te explique qué falla, y si el turno acaba con las pruebas sin pasar, la app te lo avisa. Cada aviso, una vez por turno. Reconoce npm, pytest, Go, Rust, .NET, Maven, Gradle, Make, PHPUnit y Pester, también en monorepos.
- **Actividad.** Un panel a la derecha te cuenta, como lo haría un compañero, lo que va haciendo Claude en la pestaña activa: qué archivos mira, qué cambia o crea, qué busca, a qué agentes llama y qué le dicen, qué comandos ejecuta y para qué, qué falla y qué prueba en su lugar, y al final el resultado («Listo: …»). Cada paso aparece al momento en gris y, a los pocos segundos, Haiku lo cuenta en una o varias frases cortas (dos renglones como mucho). Abajo, lo que está haciendo ahora mismo y desde cuándo. Cuando Claude enseña algo (una imagen, un PDF, una página o una web), sale «Pincha aquí para verlo»: «aquí» lo abre y, si es una imagen o un PDF, debajo va su miniatura (lo que no la tiene, como una página, se ve en grande al pasar el ratón). Las webs, solo las de la respuesta final. Se activa o desactiva en la rueda de opciones («Actividad», activada de serie); desactivada, Haiku no cuenta nada y no gasta. Activada, la pestaña vertical del borde derecho muestra u oculta la columna: oculta, Haiku sigue contando, y un punto verde en la pestaña dice si Claude está trabajando. Cuando Claude trabaja con un plan, la parte de abajo de la columna lo enseña paso a paso (un cuarto como poco; con más pasos crece para que se vean todos, hasta tres cuartos) con su estado (Terminado, Trabajando o Pendiente) y una barra de avance; el paso en curso siempre a la vista, y al terminar se pliega a su cabecera («Terminado · 6 de 6»). La columna se ensancha o se estrecha arrastrando su borde izquierdo (hasta un 20 % en cada sentido; doble clic, su tamaño normal) y recuerda el ancho.
- **Optimiza.** El botón de la cabecera de cada sesión pide a Claude que revise todo el proyecto y lo mejore sin cambiar lo que hace: limpieza, orden, eficiencia y coherencia visual. Trabaja solo, en una rama aparte de git: mide antes y después, pasa las pruebas tras cada cambio, deshace lo que falle y pide una revisión independiente. Al terminar te deja un informe y la rama para que decidas si la unes. Antes de empezar te pide confirmación. Conviene usarlo de vez en cuando (tras una tarea grande o antes de publicar), no a diario: tarda y gasta de tu plan. El botón solo aparece cuando conviene: tras muchos cambios de código, cuando un archivo se hace muy grande o cuando hace un mes de la última optimización, Haiku lee lo que más ha cambiado y, si ve problemas claros, la app te avisa con el motivo. Nunca se lanza solo; «Ahora no» lo esconde 7 días.
- **Aviso de claves y contraseñas.** Otra buena práctica para cualquier proyecto: si Claude escribe en un archivo una clave o una contraseña (de Anthropic, OpenAI, GitHub, AWS, Google, Slack o Stripe, una clave privada, una contraseña en el código, en la configuración o en una dirección de conexión), en ese momento se le pide que la pase a un archivo `.env` que git no suba, la lea desde ahí y te lo cuente. Si un `.env` con claves no está en `.gitignore`, también se lo dice. Avisa una vez por clave y archivo; la clave no se guarda ni se muestra en ningún sitio. Con «Codex asesora», lo que lleve claves no se envía a OpenAI.
- **Aviso de archivos que crecen.** Una buena práctica que vale en cualquier proyecto que abras: cuando Claude edita un archivo de código que llega a 1 000 líneas, y otra vez cada vez que crece un 20 % más (1 200, 1 440…), ClaudHome se lo dice y Claude te comenta al terminar si conviene partirlo, con su recomendación. No parte nada sin que se lo pidas, y no cuenta documentos, datos ni estilos. Si Claude cambia el archivo con un comando de la terminal en vez de con su herramienta de edición, la app no lo ve.
- **«You should know».** Las sesiones llevan encendido este plugin integrado en Claude Code: un agente aparte vigila lo que hace Claude y, cuando pasa algo que conviene saber y se te podría escapar, lo avisa con una tarjeta («Heads up» o «You should know») con las opciones «Learn more», «Know this already» y «Dismiss». Si lo activas o desactivas tú en tu configuración de Claude Code, se respeta.
- **SuperPowers.** El botón «⚡ SuperPowers» de la cabecera de cada sesión hace que Claude trabaje más a fondo en esa pestaña y no dé nada por terminado sin comprobarlo. Gasta más de tu plan y tarda más, así que va apagado: al pulsarlo explica qué hace y lo que cuesta, con «Activar». Encendido, el botón lleva un borde violeta, rosa y oro que gira mientras Claude trabaja (quieto al terminar y con «reducir animaciones») y la pestaña, un rayo. Con Codex listo, al encenderlo sale de «Codex» una estela de gas verde que envuelve el botón unos segundos, y después el botón se queda en brasas verdes mientras siga «al máximo» (`ui/sp-ignite.js`; sin estela ni gas con «reducir animaciones»). Encender o apagar reinicia la sesión de esa pestaña con la misma conversación (si Claude está trabajando, al terminar). Con él:
  - **Lo pedido y lo que das por hecho.** Al empezar una tarea, Claude apunta lo que pides y lo que darías por hecho aunque no lo digas (usos evidentes, casos límite, entradas no válidas o malintencionadas) y trabaja contra esa lista.
  - **Pasada final.** Cuando Claude va a terminar una tarea que ha cambiado algo, ClaudHome le pide pasar las pruebas (y añadir las que falten para la lógica cambiada), repasar punto por punto lo que pediste y lo que darías por hecho y, si cambió algo que se ve, revisarlo con capturas. Cierra con lo comprobado, lo pendiente y, solo si merecen la pena, hasta tres mejoras sin aplicarlas. Una vez por tarea, nunca al cerrar la sesión. En un cambio pequeño (hasta dos archivos y seis ediciones) la pasada es ligera: sin pruebas nuevas para lo que solo cambia cómo se ve y sin páginas de vista previa aparte. En «Actividad», una tarjeta resume la pasada con lo que ha visto ClaudHome (pruebas, capturas, Codex), no con lo que diga Claude.
  - **Revisión de Codex.** Si tienes Codex, revisa aunque «Codex asesora» esté apagado, y a la vez que la pasada final: empieza al pedírsela y lo que encuentra le llega a Claude al terminarla. Si en la pasada Claude cambió código, Codex le da una segunda vuelta (como mucho con razonamiento «high») mientras Claude corrige lo de la primera, o antes de terminar si la primera no encontró nada; dos vueltas como mucho. Si no se puede revisar porque lo que ha escrito Claude en la tarea lleva algo con pinta de clave (una clave de mentira en una prueba), se le pide una vez que no la deje escrita tal cual y vuelva a terminar. Codex solo revisa en repositorios git: si la carpeta no tiene, al encender SuperPowers con Codex (con el botón, no al abrir una pestaña) se crea uno local (`src/main/git-init.js`) con una foto del estado actual: un commit de «ClaudHome», sin remoto, que deja fuera en `.git/info/exclude` lo pesado, los `.env`, las claves y los archivos que parecen llevarlas. No se crea en la carpeta del usuario ni en sus carpetas generales, del sistema, de red u OneDrive, con otro repositorio dentro o con más de 5 000 archivos o 200 MB. git se lanza sin hooks, sin plantilla y sin variables `GIT_*` heredadas, y si algo falla se borra el `.git` a medias (solo si lleva la marca de ClaudHome). Sin git, el botón no se queda en brasas.
  - **Revisión por capturas.** La herramienta `capturar_pantalla` abre una página del proyecto (un `.html` de su carpeta, de sus copias de trabajo de git o lo que sirve en `localhost`) en una ventana invisible a 390, 1024 y 1440 px y le devuelve a Claude las imágenes, con aviso de desbordes y errores de la consola. De los CDN públicos conocidos (jsDelivr, unpkg, cdnjs, Google Fonts, Bootstrap, Font Awesome…) carga solo estilos, fuentes, guiones e imágenes por https, para que la captura se parezca a la página real, y queda anotado en el «Log»; lo demás que la página pida a internet no se carga y se le avisa. Se le pide que capture la página real con el servidor del propio proyecto, sin copias estáticas. Las capturas se guardan dos días en `%APPDATA%\Claudes\capturas`.
  - **Método y agentes.** Esfuerzo alto como mínimo y tres habilidades del plugin incluido: verificar antes de dar algo por hecho, depurar buscando la causa y pruebas primero (sin borrar nunca código que funciona). Están basadas en [obra/superpowers](https://github.com/obra/superpowers) (MIT), adaptadas. Como mucho dos agentes a la vez, que no lanzan otros: comprueban en paralelo mientras Claude sigue, y solo edita Claude.
  - **Ideas para el proyecto.** Tras unas cuantas tareas, como mucho una vez al día, Sonnet en un proceso aparte mira el resumen del proyecto (el del Workflow, con lo que parezca una clave tapado) y propone una mejora visual o funcional. Solo se enseña si la ganancia es alta, la confianza también, el esfuerzo es poco y el riesgo no es alto; si tienes Codex, además tiene que coincidir. Sale encima de la terminal, sin quitarle el foco y con Claude parado: «Pruébalo en una rama aparte» (Claude la prueba en una copia de trabajo de git con su rama, sin tocar la tuya), «Más tarde» (mañana) o «No me interesa» (no vuelve ni nada parecido; con varios rechazos, solo se enseñan las de ganancia máxima). Lo enviado queda en el «Log».
  - **Lo que aporta.** La tarjeta del proyecto cuenta, de las tareas que cambian algo, cuántas se han hecho con SuperPowers y cuántas sin, lo que tardan de media, en cuántas la pasada final corrigió algo, las pruebas en verde al terminar y lo que encontró Codex.
- **Workflow.** El botón «Workflow» de la cabecera de cada sesión enseña cómo funciona el proyecto en un mapa que cabe en una pantalla: de dónde entran los datos, qué bloques hay (interfaz, núcleo, procesos o contenedores, datos y servicios de internet), cómo se conectan, qué se repite solo (↻), qué pide una credencial (una llave turquesa: una sesión, un token o una clave; es un requisito, no un error) y qué bloquea o prohíbe la comunicación (✕). Además, «▶ Empieza aquí» (verde, late) marca por dónde arranca todo, un escudo violeta señala los datos sensibles y una flecha lila punteada lo que trabaja en segundo plano. Cada símbolo tiene su fila reservada en el bloque, el hueco entre columnas crece con su etiqueta y la leyenda solo muestra lo que hay en el mapa. Tiene cinco niveles de zoom (vista general, bloques, piezas, detalle y detalle ampliado): de lejos se ven los bloques; al acercarte, las piezas de cada uno; más cerca, qué hace cada pieza y sus archivos. Cada pulsación de + o − va exactamente un nivel, y se apagan en el primero y en el último. Rueda o pellizco para acercar, arrastrar para moverse, pulsar un bloque para entrar y doble clic o «Ver todo» para volver. Lo dibuja un modelo aparte, sin tocar tu sesión de Claude ni su conversación: Codex si lo tienes con sesión de ChatGPT (no gasta de tu plan de Claude) o, si no, Claude en un proceso propio (Sonnet el primer mapa, Haiku al actualizarlo). El botón «Stack Tecnológico» abre un recuadro con qué está hecho el proyecto (versión y para qué de cada pieza); va cerrado de entrada para dejar todo el espacio al mapa. El mapa se prepara solo al entrar en un proyecto (abrir su pestaña o cambiar a ella), así que al pulsar «Workflow» ya está; se guarda por proyecto y se actualiza cada vez que vuelves a entrar si el proyecto ha cambiado y, con la ventana abierta, cada 5 minutos si hay cambios. Varios proyectos se hacen de uno en uno. Sin Codex y con tu plan de Claude al 80 % o más, nada de esto se hace solo, para no quitarle margen a tu trabajo: el botón y «Rehacer» sí lo hacen.
- **Log.** En la rueda de opciones, «Log» muestra lo que sale de este equipo a través de Claude. ## Cómo funciona por dentro

- Electron + xterm.js + node-pty. Cada pestaña lanza `claude.exe` en una pseudoterminal.
- **Conversaciones.** Cada pestaña recuerda el identificador de su conversación y la retoma con `claude --resume <id>`. Si esa conversación ya no existe, empieza una nueva. La opción «Continuar la última conversación de esa carpeta» solo se aplica al crear la pestaña.
- **Estado.** Cada sesión arranca con `--settings <archivo>`, que añade hooks HTTP hacia un servidor local de la app (`src/main/hooks.js`). No se modifica tu configuración de Claude Code y tus hooks y mods siguen funcionando.
- **Dictado.** El mismo archivo de `--settings` activa el [dictado de Claude Code](https://code.claude.com/docs/en/voice-dictation) en modo «mantener» (`voice.enabled`, `voice.mode: "hold"`): la grabación y la transcripción las hace Claude Code. Claude Code reconoce la tecla mantenida por sus repeticiones, así que el botón del micrófono solo decide si las repeticiones de la barra espaciadora llegan a la sesión. Por eso se aplica al momento, sin reiniciar nada. Si tu configuración de Claude Code no fija `language`, ClaudHome añade `"language": "spanish"` para que el dictado sea en español; ese ajuste también hace que Claude responda en español. Si pones tu propio `language` en `~/.claude/settings.json`, se usa el tuyo.
- **Actualización.** Solo en el ejecutable instalado. Cada versión se publica en GitHub como un «release» con dos archivos: `ClaudHome-win32-x64.zip` (la carpeta del programa) y `latest.json` (`version`, `file`, `size` y `sha256` de ese zip). Al arrancar y cada 6 horas, la app lee el `latest.json` del último release y compara su versión con la instalada. Los cambios que enseña salen de las secciones de `CHANGELOG.md` en `main` posteriores a la versión instalada y hasta la publicada; al ejecutar desde el código se lee el `CHANGELOG.md` local. Para actualizar descarga el zip en `%LOCALAPPDATA%\Claudes-update`, comprueba su tamaño y su SHA-256 y lo descomprime con el `tar.exe` de Windows. Después comprueba el acceso directo del escritorio. Windows no deja sustituir un programa abierto, así que al cerrarse ClaudHome lanza `src/main/install-update.js` con el `Claudes.exe` recién descargado en modo Node (`ELECTRON_RUN_AS_NODE`), sin depender de que haya Node.js en el equipo. Ese instalador espera a que ClaudHome termine, renombra la carpeta del programa a `<carpeta>.anterior` y pone la nueva en su sitio. Como Windows tampoco deja mover la carpeta de un programa en marcha, y el instalador corre desde la nueva, mueve su contenido pieza a pieza (el propio ejecutable sí se puede mover). Si se eligió reiniciar, vuelve a abrir Claudes. Si algo falla, recupera la anterior. Cada actualización deja su registro en `logs\actualizacion-<fecha>.log`, y al volver a abrir ClaudHome un aviso dice si se instaló.
- **Cierre ordenado.** La app envía `Esc` (interrumpe el turno), escribe la petición de resumen y espera el hook `Stop`; después deja que Claude salga solo con `Ctrl+C`. Gasta un turno corto de Claude por sesión.
- **Codex.** `codex login status` dice si hay sesión de ChatGPT. Las herramientas de Codex (`segunda_opinion` siempre; `generar_imagen` si las imágenes están activadas) salen de un servidor MCP local (`src/main/mcp.js`, servidor `claudhome-codex`), que se pasa a cada sesión con `--mcp-config` en cuanto hay Codex con la cuenta de ChatGPT; la lista se mira en cada `tools/list`. Para una imagen, la app ejecuta `codex exec` en modo solo lectura y copia la imagen resultante a la carpeta de la sesión. Cada imagen consume una generación del plan de Codex. Las sesiones abiertas antes de activar el indicador necesitan reiniciarse para recibir la herramienta (la app lo ofrece).
- **Registros.** Con la depuración activada, cada arranque de Claude lleva `--debug-file` y escribe en `%APPDATA%\Claudes\logs\<fecha>-<hora>-<pestaña>.log` (horas en UTC, formato de Claude Code). La app añade su propio `claudes-<fecha>.log` (hora local) con arranques, hooks recibidos, cambios de estado, notificaciones, peticiones a Codex y errores. Se borran a la semana o al pasar de 300 MB. El interruptor afecta a las sesiones que se abran o reinicien después de cambiarlo.
- **Imágenes pegadas.** Una imagen copiada se guarda en `%TEMP%\Claudes-pegado` y se pega su ruta; se borran solas a la semana.
- **Contexto del proyecto.** Se guarda con la pestaña en `state.json`; de los documentos solo se guarda su ruta, no se copian. Al arrancar la sesión, `src/main/context.js` escribe el resumen (la nota y la lista de documentos con su ruta) en `%APPDATA%\Claudes\contexto\<pestaña>\instrucciones.md`, y se pasa a Claude con `--append-system-prompt-file`. Los Word se pasan a texto en esa misma carpeta, porque Claude no lee `.docx`. Para que Claude lea los documentos sin preguntar, cada uno lleva una regla `Read(//c/…)` en los ajustes de la sesión, y cada dominio de los enlaces una `WebFetch(domain:…)`. El título y el aviso de inicio de sesión de un enlace se obtienen al añadirlo, con `net.request` de Electron (usa el proxy del sistema y sigue las redirecciones para ver dónde acaba la página). Si el contexto cambia con la sesión abierta, el hook `UserPromptSubmit` le da el resumen nuevo con el siguiente mensaje (`additionalContext`). No se usa `--add-dir`, porque Claude Code preguntaría al arrancar si confías en cada carpeta.
- **Llenado de la conversación.** Cada sesión lleva una línea de estado (`statusLine` en su `--settings`) que no muestra nada: solo reenvía con `curl` a la app lo que Claude Code le pasa (`context_window.used_percentage` y el tamaño de la ventana). Si tienes tu propia línea de estado en `~/.claude/settings.json`, se respeta y esa sesión se queda sin indicador.
- **Límite de uso y tokens.** La misma línea de estado trae `rate_limits.seven_day` y, en los planes que lo tienen, `rate_limits.five_hour` (`used_percentage` y `resets_at`), que Claude Code saca de las cabeceras de la última respuesta de la API. Son de la cuenta, así que vale lo que llegue de cualquier pestaña: dentro de un mismo periodo se queda el porcentaje más alto, y una renovación anterior a la conocida se descarta (una sesión parada puede repetir datos viejos). Se guarda en `state.json` para mostrarlo nada más abrir la app. Los tokens los cuenta `src/main/limits.js` en las conversaciones de `~/.claude/projects/**/*.jsonl`, sumando una sola vez cada respuesta (`message.id` + `requestId`). Las respuestas de los subagentes (`<conversación>\subagents\*.jsonl`) llevan el `sessionId` de su conversación y suman en ella. La conversación de cada pestaña es la del arranque y, tras un `/clear`, la que traen los hooks. Cada archivo se lee solo por donde iba la vez anterior; los de más de 8 días se saltan, salvo los de una pestaña abierta, y si uno saltado vuelve a crecer se lee entero. Tras una respuesta recuenta, como mucho cada 10 s, solo las conversaciones de las pestañas abiertas (y sus subagentes); la carpeta entera, que es donde aparece lo gastado fuera de ClaudHome, se recorre cada minuto. Pasada la hora de renovación, cuenta desde entonces hasta que el siguiente mensaje traiga el porcentaje nuevo.
- **Plugins.** Los plugins que trae la app están en `src/plugins/`. Al arrancar se copian a `%APPDATA%\Claudes\plugins`, porque Claude Code no puede leerlos dentro de `app.asar`, y cada sesión los carga con `--plugin-dir`, sin instalar nada en tu Claude Code. El hook de `explanatory-output-style` es un script de bash que Claude Code ejecuta con Git Bash. Por eso solo se pasa si la app encuentra Git Bash (en su ruta de instalación o junto al `git.exe` del PATH) y si no lo tienes ya activado en tu `~/.claude/settings.json` (`enabledPlugins`). `frontend-design` es una copia sin cambios del marketplace oficial (Apache 2.0, con su `LICENSE`): solo trae una skill, sin hooks, así que se carga también sin Git Bash. No se pasa si en tu `enabledPlugins` ya está `frontend-design@claude-plugins-official`, activado (se cargaría dos veces) o apagado (lo has decidido tú).
- **Uso de Codex** (`codex.js`, `readLimits`). La app lanza `codex app-server` (sin claves de API en el entorno, en la carpeta del usuario), le envía por la entrada estándar `initialize`, `initialized` y `account/rateLimits/read` (JSON-RPC) y lo cierra; tarda alrededor de un segundo y no consume nada del plan. De la respuesta se toma la ventana semanal (`windowDurationMins` 10080) o, si no hay, la más larga, con `usedPercent`, `resetsAt` y el tipo de plan. Se pide tras detectar Codex, cada 10 minutos y 4 s después de cada trabajo de Codex, y viaja a la interfaz con el estado de Codex (`codex:changed`).
- **Segunda opinión y crítica de planes** (`review.js`, `codex.js`). La herramienta `segunda_opinion` (pregunta, ámbito y archivos relevantes) ejecuta `codex exec --sandbox read-only --ephemeral --skip-git-repo-check --json -C <proyecto>` con el mismo modelo y razonamiento que la revisión, sin claves de API en el entorno y con la petición por la entrada estándar; de la salida JSON se toma el último mensaje de Codex. Antes se comprueba la sesión de ChatGPT y que la pregunta no lleve claves. Si Claude Code deja de esperar (Esc), la llamada MCP se corta y Codex se para. Para los planes, los ajustes de cada sesión llevan un segundo hook `PreToolUse` solo para `ExitPlanMode` (`matcher`), con 900 s de espera y su propia dirección (`PlanReview`), que no se le pasa a la interfaz. Con «Codex asesora» encendido, la primera vez en cada turno Codex critica el plan (`tool_input.plan`) junto con la petición del usuario, y la app contesta `permissionDecision: "deny"` con la crítica: Claude ajusta el plan y lo vuelve a presentar, y esa segunda vez pasa sin más.
- **Cuándo entra Codex** (`review.js`, `advisorNote`). Con «Codex asesora» encendido, el hook `UserPromptSubmit` le dice a cada sesión cuándo pedir `segunda_opinion` por su cuenta (`ADVISOR_ON`) y cómo encontrarla con ToolSearch; se repite cuando la conversación ya no lo tiene: al volver a arrancar la sesión, tras /clear (cambia su `session_id`), tras resumirse (hook `PostCompact`; `PreCompact` y `PostCompact` llegan como hooks HTTP con el mismo `session_id`) y cada 30 mensajes; al apagarlo se le dice que ya no la pida (`ADVISOR_OFF`). Hace falta porque con muchos servidores MCP, Claude Code difiere las herramientas (en la prueba real, 230) y Claude solo ve su nombre, no su descripción. Nivel de razonamiento de Codex (`model_reasoning_effort`): revisión del código, `medium` hasta 20 líneas cambiadas, `high` hasta 300 y `xhigh` por encima o si cambia algo de seguridad, despliegue o datos (por la ruta: auth, login, password, token, .env, docker, deploy, migraciones, .sql…); crítica de un plan, `high` y `xhigh` si pasa de 2 500 caracteres; segunda opinión, la `profundidad` que pida Claude (`rapida`, `normal`, `a_fondo` → medium, high, xhigh) o, si no la pide, `xhigh` en seguridad, plan y problema y `high` en lo demás.
- **Interruptor «Codex asesora»** (`review.js`). Se guarda en `state.json` (`codexReview`; sin valor, apagado). Apagarlo vale al momento: la herramienta `segunda_opinion` sigue en la lista de la sesión, pero contesta que está apagado sin llamar a Codex, y no hay crítica de planes ni revisión. Todas las llamadas a Codex como asesor llevan `--ignore-user-config` (sin la configuración del usuario ni sus servidores MCP, que no respetan el modo solo lectura), `--ignore-rules` (sin sus reglas de comandos permitidos) y `-c features.X=false` para `computer_use`, `browser_use`, `browser_use_external`, `in_app_browser`, `apps` e `image_generation` (con `-c`, una función que no exista en otra versión se ignora; con `--disable`, Codex fallaría). De la configuración del usuario solo se conservan dos ajustes: dónde guarda la sesión (`cli_auth_credentials_store`) y la zona protegida de Windows (`[windows] sandbox`), sin la cual Codex bloquea hasta un `git status` y no puede leer el proyecto. Si en Windows falta `[windows] sandbox` en el config.toml de Codex, la rueda lo advierte bajo «Codex asesora» (no podrá leer el proyecto); y si en una consulta su salida o su registro muestran comandos rechazados («blocked by policy») o accesos denegados, la app avisa con la solución: la revisión no se da por revisada, el plan pasa sin crítica y a la segunda opinión se le antepone un aviso para Claude. La carpeta se le pasa solo como directorio de trabajo y con su ruta completa: con `-C` y una ruta abreviada (`NOMBRE~1`), la zona protegida le niega la lectura. El asesor solo se ofrece si `codex exec --help` admite `--ignore-user-config` y `--ignore-rules`; con una versión antigua, el indicador pide actualizarla. Con la instalación de npm, la app no lanza `codex.cmd` a través de `cmd.exe`: ejecuta su `codex.js` con `node` (el de al lado o el del `PATH`), así que las rutas con espacios o de red van tal cual. La herramienta `segunda_opinion` está en las sesiones en cuanto Codex está instalado (si falta la sesión de ChatGPT, lo dice), se lanza en la carpeta del agente que la pide (la de su `PreToolUse`) y antes mira que la pregunta y los archivos que señala no lleven claves. Un plan de más de 60 000 caracteres no se critica, y se avisa. Apagar el interruptor para lo que esté en marcha. La app sigue cada turno con los hooks: `UserPromptSubmit` lo empieza (y anota si el interruptor estaba encendido) y `PostToolUse` de Edit, Write, MultiEdit o NotebookEdit sobre un archivo de código o HTML lo marca como «ha editado código». Al llegar `Stop`, si toca, la app retiene la respuesta del hook mientras corre `codex exec review --uncommitted --ephemeral` con `gpt-6.2-astra`, `model_reasoning_effort="xhigh"`, `review_model` igual, `sandbox_mode="read-only"` y `model_provider="openai"`, sin `OPENAI_API_KEY` ni `CODEX_API_KEY` en el entorno y con `NoDefaultCurrentDirectoryInExePath=1` para que Windows no busque programas en la carpeta del proyecto. Justo antes se comprueba con `codex login status` que la sesión es la de ChatGPT; no se usa `forced_login_method`, que borra las credenciales de Codex si no coinciden. Si no quedan cambios sin confirmar (Claude ya los confirmó), no se lanza. Se revisa el repositorio de los archivos de código editados (con las rutas resueltas en el momento de editarlos): si son de varios, ninguno. El repositorio se busca en disco (`.git` en la carpeta o en una superior), sin lanzar git. Antes de lanzar Codex, `secrets.reviewInput` repasa lo que va a recibir: `git diff --cached` y `git diff` por separado (lo preparado y lo no preparado, también las líneas borradas) y los archivos nuevos que git no deja fuera, también en UTF-16. git se lanza con su ruta del `PATH`, con el formato del diff fijado, sin diff externos, sin `textconv` y sin `core.fsmonitor`; un diff que no se entiende cuenta como no comprobado. Si pulsas Esc, la comprobación se para. Al cerrar la app se paran las revisiones en marcha, y lo que llegue de un turno ya pasado no se le devuelve a Claude. Si encuentra claves, o no puede comprobarlo todo (más de 20 MB de diff, archivos nuevos de texto de más de 2 MB, más de 2 000 archivos nuevos), no se revisa. La salida hacia OpenAI se anota en el «Log» antes de lanzar Codex. Una salida sin hallazgos que dice que no ha podido revisar cuenta como fallo, no como «sin problemas». Si hay hallazgos, contesta `{decision: "block", reason}` y Claude sigue trabajando con ellos. Hay una sola ronda por turno: el segundo `Stop` ya no se revisa, lleve o no `stop_hook_active`, y lo que llegue de un turno anterior no cambia el estado del actual. El hook `Stop` tiene un tiempo de espera de 900 s (los demás, 5 s) y la app contesta siempre antes; si se agota su propio plazo, cancela la revisión. Si Claude Code deja de esperar, la conexión se cierra y la revisión se cancela (`taskkill /T`). Con la depuración activada, cada revisión deja su salida completa en `logs/revision-codex-*.log`.
- **Interruptor «Resumido».** Se guarda en `state.json` (`briefMode`). El plugin explicativo solo actúa al arrancar (hook `SessionStart`), así que la app recuerda qué estilo tiene cada sesión. Si no coincide con el interruptor, se lo dice con el siguiente mensaje mediante el `additionalContext` del hook `UserPromptSubmit`, junto con el contexto del proyecto si también cambió. Con el interruptor encendido, las sesiones nuevas arrancan sin el plugin. Al volver al modo explicativo, el texto que recibe Claude es el del propio `session-start.sh` del plugin, que también se usa si el plugin no se pudo cargar (sin Git Bash).
- **Actividad** (`src/main/narrator.js`, `ui/activity.js`). Los pasos salen de los hooks: `PreToolUse` (cada herramienta, también las de los agentes, que llevan `agent_id` y `agent_type`), `PostToolUseFailure` (el error), `SubagentStart` y `SubagentStop` (con la última respuesta del agente), `PermissionRequest` y `Notification` (espera al usuario) y `Stop` (con `last_assistant_message`; si se le retiene por las pruebas o va a revisar Codex, se dice). Lo que Claude escribe entre pasos se lee del registro de la conversación (`transcript_path`, solo lo nuevo y solo los mensajes de Claude, no los de sus agentes) y va delante de la herramienta que lo sigue; llega al registro un paso más tarde. Los comandos se describen con palabras fijas (pruebas, git, dependencias…). Lo que se le pasa a Haiku es lo que ya tiene la conversación de Claude (la petición, los pasos, lo que escribe Claude, los errores y el principio de cada cambio), con las contraseñas y tokens tapados (`redact` de netlog.js y `maskSecrets` de secrets.js, con los patrones del aviso de claves); por eso no se apunta en el «Log». Haiku se lanza sin `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` ni Bedrock/Vertex (también para «Optimiza»): siempre con la cuenta del usuario, y si no la hay, no se pregunta. Cada tarea (cada mensaje del usuario) va aparte: lo que quede de una no se mezcla con la siguiente. Si Codex revisa al pararse, el final espera a su resultado (`review:result`): si no encuentra nada, ahí termina la tarea. Los informes de agentes en segundo plano (`<agent-message>`) y los avisos de tareas (`<task-notification>`) llegan como `UserPromptSubmit` pero no son del usuario. Lo del panel se procesa después de contestar al hook; al cerrar el panel se cortan las preguntas en marcha (con `taskkill /T` en Windows, que con una instalación por npm se lanza cmd.exe). Con el panel abierto, cada 2–3 s se juntan los pasos nuevos de una pestaña y se le pregunta a Haiku (`haiku.js`: el mismo `claude -p --model haiku` sin herramientas, MCP, configuración ni sesión guardada que usa «Optimiza»): recibe la petición del usuario, lo último que ya contó y los pasos, y contesta `{lineas: [{tipo, texto}]}` (1 a 3 frases de 20 palabras como mucho). Sus líneas sustituyen a las grises; si no contesta, se quedan las grises, y tras 3 fallos seguidos descansa 5 minutos. Una pregunta a la vez por pestaña y tres en total. Se guarda en `state.json` si está activada (`activityEnabled`, la rueda; activada de serie) y si la columna está a la vista (`activityOpen`, la pestaña lateral); lo de cada pestaña, solo en memoria (150 líneas; dormir la pestaña no lo borra, cerrarla sí).
- **Plan de la tarea** (`src/main/plan.js`, `ui/plan.js`). Con los modelos nuevos, Claude Code trae apagada su lista de tareas; ClaudHome la enciende en cada pestaña (`CLAUDE_CODE_ENABLE_TODO_TOOLS=1`, salvo que el usuario tenga puesta la variable) y, delante del contexto del proyecto (`--append-system-prompt-file`), le pide a Claude que en los trabajos de tres pasos o más apunte cada paso con `TaskCreate` y lo marque con `TaskUpdate` al empezar y al acabar (y que convierta en tareas un plan aprobado en modo planificación). El estado sale de los hooks `PostToolUse` del hilo principal (no de los agentes): el número de cada tarea llega en la respuesta de `TaskCreate`; `TaskUpdate` la cambia o la borra; `TodoWrite` (modelos anteriores) trae la lista entera. No se lee `~/.claude/tasks`, para no mezclar tareas de otras sesiones. Un plan nuevo empieza con el siguiente encargo del usuario si el anterior estaba terminado; con `/clear` se vacía.
- **Workflow** (`src/main/workflow.js`, `workflow-digest.js`, `ui/workflow.js`, `ui/workflow-layout.js`). Cómo se hace el mapa (método, forma de escribir, cómo se presenta y formato JSON, con un ejemplo) está en una sola guía con formato de skill, `src/workflow/SKILL.md`: los dos motores la reciben entera, así que se hace y se presenta siempre igual. Solo la usa el botón: la sesión principal de Claude no la carga. Cada mapa guarda el número `version` de la cabecera de la guía con el que se hizo. Solo ese número cuenta: retocar el texto no toca los mapas hechos; subirlo hace que cada mapa se complete al entrar en su proyecto, con el modelo rápido y sin rehacerlo desde cero (para no gastar de más en cada versión). Primer mapa y «Rehacer»: Codex con razonamiento `medium` o Sonnet; actualizaciones (cambios del proyecto o guía nueva): Codex `low` o Haiku. Al actualizar, las reglas y bucles ya comprobados del mapa anterior se conservan si el modelo los devuelve tal cual. El modelo nunca lee la carpeta: la app elige lo que se le envía. Con git, la lista de archivos es la de `git ls-files -co --exclude-standard`; sin git, se recorre la carpeta sin `node_modules`, `dist`, `.venv` y similares. Nunca entran enlaces, binarios, `.env` ni archivos de claves (`.pem`, `id_rsa`, `credentials`…). Se envían el árbol, los manifiestos (package.json, docker-compose, Dockerfile, README…) y, de cada archivo de código, el principio y las líneas que dicen cómo se conecta (imports, funciones, rutas, temporizadores, procesos que lanza), hasta unos 110 000 caracteres; todo pasa por `maskSecrets`. Codex se lanza con `askCodex` en solo lectura, efímero y desde una carpeta vacía (razonamiento `medium` el primer mapa, `low` al actualizarlo); sin Codex, `claude -p --model sonnet|haiku --tools ""` sin MCP, sin la configuración del usuario y sin guardar la sesión. La respuesta es JSON con un esquema fijo: `validate` recorta cantidades y longitudes, quita referencias rotas, tapa lo que parezca una clave y descarta cada regla o bucle cuyo archivo de origen no se le enseñó. La huella del proyecto (ruta → hash del contenido; los archivos con el mismo tamaño y fecha no se releen) dice qué ha cambiado; el siguiente ciclo se programa 5 minutos después de acabar el anterior y solo con la ventana abierta. Al cerrarla se corta lo que se estuviera actualizando, pero el primer mapa sigue. El mapa se guarda de una vez en `<datos>\workflow\<hash>.json`. El dibujo (`workflow-layout.js`, puro) pone columnas fijas por tipo de bloque, los servicios de internet en una banda arriba, flechas de borde a borde entre columnas contiguas y por un carril de abajo entre columnas alejadas; los niveles de detalle dependen de los píxeles por unidad del lienzo, y las etiquetas de las flechas guardan su tamaño en pantalla. Para pruebas: `CLAUDES_WORKFLOW_ENGINE=codex|claude` y `CLAUDES_WORKFLOW_EVERY_MS`.
- **Optimiza** (`src/main/optimize.js`, `ui/optimize.js`). Solo con la sesión en reposo. `optimize:check` mira con git (el del PATH o el que hay junto a su bash) si la carpeta es un repositorio, en qué rama está y si tiene cambios sin confirmar; sin git instalado, no sigue. Tras confirmar, `optimize:arm` lo vuelve a comprobar y lo guarda en la pestaña, y la interfaz escribe una petición corta (`OPTIMIZE_PROMPT`). En su `UserPromptSubmit`, si empieza por `OPTIMIZE_START` y llega en menos de 2 minutos, el hook añade una vez las instrucciones completas: rama `optimiza-AAAAMMDD-HHMMSS` (o `git init` y un commit inicial si no hay git; los cambios sin confirmar, tal cual en un primer commit), mediciones antes y después, pruebas para lo que no las tenga, un commit por mejora con pruebas, lint y build, sin cambiar comportamiento ni añadir dependencias, revisión independiente (`segunda_opinion` o un subagente) e informe. La rama no se une ni se sube. No cambia el modo de permisos: si no se aceptan los cambios automáticamente (Mayús+Tab), Claude pide permiso.
- **Optimiza recomendado** (`src/main/optimize-hint.js`, `optimize-check.js`). El botón está oculto salvo cuando se recomienda. Tras cada `PostToolUse` con éxito de Edit, Write, MultiEdit o NotebookEdit sobre código dentro de la carpeta de la pestaña (después de contestar al hook), se suma un cambio y se cuentan las líneas del archivo (hasta 2 MB). Por proyecto, en `state.json` (`optimizeHints`, hasta 60 proyectos y 300 archivos cada uno): cambios, líneas de cada archivo, las de la última optimización, cuándo fue, «Ahora no» y si ya se avisó. Las señales pasan el umbral con 150 cambios, con un archivo de 800 líneas o más que no lo fuera ya al optimizar (o que haya crecido un 15 %), o con 30 días y al menos 40 cambios. Entonces se pregunta a Haiku, en segundo plano: `claude -p --model haiku --tools "" --strict-mcp-config --no-session-persistence --disable-slash-commands --setting-sources "" --output-format json`, en una carpeta vacía y con la pregunta por la entrada estándar (sin herramientas, servidores MCP, configuración ni sesión guardada; corta a los 2 minutos). Recibe las señales y los archivos que más han cambiado en la ronda (hasta 8, 12 000 caracteres cada uno y 60 000 en total; sin los que `scanText` ve con claves), y contesta `{recomendar, motivo}`. Se recomienda solo si dice que sí, con su motivo primero. Se le pregunta una vez por ronda (entre optimizaciones); si dice que no, otra vez a los 7 días y con 30 cambios más; si no se le puede preguntar, valen las señales y se reintenta al día siguiente. Cada archivo enviado queda en el «Log». Al pasar a recomendado se avisa a todas las pestañas del proyecto (`optimize:hint`) y, la primera vez, con un mensaje. Cuando el hook da las instrucciones de «Optimiza», se pone a cero, y lo que cambie Claude en ese turno solo actualiza el punto de partida. «Ahora no» (`optimize:snooze`) lo calla 7 días. Nunca lanza nada.
- **Pruebas antes de terminar** (`src/main/testcheck.js`). Con los hooks, la app sigue cada turno.
  - **Cambios.** Un `PostToolUse` (con éxito) de Edit, Write, MultiEdit o NotebookEdit sobre código apunta un cambio y busca en segundo plano su proyecto de pruebas: la carpeta más cercana hacia arriba con pruebas, sin pasar de la carpeta de la pestaña, de la que tiene `.git` ni de 12 niveles (4 fuera de la pestaña). La carpeta personal y la raíz del disco no cuentan; dentro de `tests/` el proyecto es el que la contiene, salvo que haya un repositorio propio por el camino. La búsqueda no bloquea la app: tiene 3 s de plazo (agotado, deja de leer, y en ese disco no se vuelve a buscar durante 2 minutos), lee manifiestos de hasta 256 KB y guarda el resultado (5 minutos si hay pruebas, 1 si no). Al tocar un manifiesto o una prueba se olvida lo guardado y se vuelve a mirar lo ya apuntado en el turno. Ante la duda, no se pide nada.
  - **Qué son pruebas.** `package.json` con un `test` que no sea el de npm por defecto (admite BOM; se propone con el gestor que declare `packageManager` o el de su archivo de bloqueo: npm, yarn, pnpm o bun), configuración de pytest o archivos `test_*.py` (también en subcarpetas de `tests/`), `go.mod` con algún `*_test.go`, `Cargo.toml`, un proyecto de pruebas de .NET, Maven o Gradle con `src/test` (con su `mvnw`/`gradlew`), un `Makefile` con `test:`, `phpunit.xml` o `*.Tests.ps1`.
  - **Órdenes de pruebas.** De cada `PostToolUse` o `PostToolUseFailure` de Bash o PowerShell se mira la orden entera (`hooks.js` la pasa aparte en `shell`, con el final de su salida; al registro solo va el principio). La línea se trocea por `&&`, `||`, `;`, `|` y saltos de línea respetando comillas, escapes, comentarios, «here-documents» y bloques `@'…'@` (el mensaje de un commit no es una orden), y de cada orden se miran el ejecutable (sin ruta ni `.cmd`/`.exe`) y sus argumentos, a través de envoltorios (`sudo`, `timeout`, `uv run`, `npx`, `bash -c`, `cmd /c`…) y con el `cd`, `--prefix` o `-C` previo (sin que se quede puesta la carpeta de un subproceso o de un `pushd`, y traduciendo `/c/…` de Git Bash). No cuentan la ayuda ni los listados (`--collect-only`, `--list-tests`…) ni lo que puede no haberse ejecutado (`lint || npm test`, o `if …; then npm test; fi` si no se ve que hayan corrido). Una línea puede pasar las de varios proyectos. Las de un «workspace» (`yarn workspace web test`, `npm test -w web`, `pnpm -r`, `turbo`, `nx`, `lerna`) o las lanzadas desde una carpeta sin pruebas propias dan por probados los proyectos de dentro: todos, o solo los que nombren (`-w web`, `--filter web`; lo que no se reconoce no da nada por probado). Solo cubren lo cambiado antes de lanzarlas (`PreToolUse` y `PostToolUse` se emparejan por `tool_use_id`).
  - **Cómo han ido.** Por cómo termina la línea: `PostToolUseFailure` es que ha salido con error. Si eso no lo aclara (`npm test | tail`, `npm test; git status`, `npm test || true`), por el resumen que escriben las herramientas de pruebas (`ℹ fail 1`, `1 failed`, `FAILED (failures=1)`, `BUILD FAILED`…). En PowerShell el código es el de la última orden nativa, vaya o no por una tubería; `Invoke-Pester` termina bien aunque fallen pruebas, así que manda su resumen, y el fallo de un `grep` que no encuentra nada no es el de las pruebas. Si el aviso de Claude Code con el resultado pasa de 64 KB se lee entero (hasta 1 MB); más allá, no se da nada por visto. Las lanzadas en segundo plano cuentan como pasadas: Claude Code avisa a Claude cuando terminan y, si luego corrige algo, el cambio queda otra vez pendiente. Si no se puede saber (`npm test && git commit` que falla, unas pruebas que no llegaron a lanzarse), no cuentan. El resultado de unas pruebas lanzadas antes no tapa el de unas posteriores.
  - **Al llegar `Stop`.** Se contesta `{decision: "block", reason}` en dos casos, cada uno una vez por turno y nunca en el de cerrar la sesión: (1) algún proyecto tiene cambios sin pruebas después: se le pide que las pase, con el comando y la carpeta; (2) las últimas pruebas de un turno con cambios han fallado: se le pide que lo corrija o que le explique al usuario qué falla. Si el turno se para con las pruebas sin pasar, el aviso `Stop` lleva `testsFailing` y la interfaz lo dice con un mensaje y en la notificación (junto al de la revisión de Codex, si la hay, para que no lo tape). La orden se nombra sin argumentos ni variables (`npm test`): pueden llevar claves. La revisión de Codex va en el `Stop` siguiente (aunque llegue con `stop_hook_active`), y su aviso pide volver a pasar las pruebas si se corrige algo.
- **Aviso de claves y contraseñas.** `src/main/secrets.js`. Tras cada `Edit`, `Write`, `MultiEdit` o `NotebookEdit`, la app lee el archivo (hasta 2 MB, no binarios, nunca dentro de `.git` o `node_modules`) y busca formatos conocidos de claves y nombres como `password`, `api_key` o `secret` con un valor. Descarta los valores de ejemplo (`YOUR_API_KEY`, `xxx`, `${VAR}`, `<password>`…), las referencias a variables y lo que parece código. Si encuentra algo nuevo, añade el aviso al `additionalContext` del `PostToolUse`, junto al de crecimiento. De cada clave recuerda solo una huella de 12 caracteres (SHA-256) por proyecto y archivo, en `state.json` (`secretWarnings`). Un `.env` es el sitio de las claves: solo se avisa si el proyecto usa git y `git check-ignore` dice que no lo deja fuera. `git` se busca únicamente en las carpetas absolutas del `PATH`. Las expresiones tienen todos sus tramos acotados, para que una línea enorme (código minificado) no deje colgado el proceso principal. Lee UTF-8 y UTF-16 (lo que escribe PowerShell 5 con `>`), con saltos de línea de Windows, y entiende los comentarios `#` al final de una línea de `.env` o YAML. Cada aviso tras una edición tiene 1,5 s para decidir; la respuesta sale a los 1,7 s como mucho con los que hayan llegado, y solo se anota como avisado lo que de verdad llega a Claude. Antes de una revisión de Codex se comprueba lo que va a recibir (ver «Codex asesora»). Como el de crecimiento, no ve lo que Claude cambia con comandos.
- **Aviso de archivos que crecen.** `src/main/growth.js`. El hook `PostToolUse` de `Edit`, `Write`, `MultiEdit` y `NotebookEdit` trae la ruta del archivo; la app cuenta sus líneas y, si llega a un escalón (1 000 y después un 20 % más cada vez), contesta al hook con `additionalContext`, que Claude Code le pasa a Claude en ese mismo turno. De los avisos grandes solo se lee el principio, pero la ruta va al principio. Se recuerda por proyecto (la carpeta de la pestaña) con cuántas líneas se avisó de cada archivo, en `state.json` (`fileGrowth`), para no repetirlo hasta el siguiente escalón; si el archivo baja de 1 000 líneas se olvida. Lo que Claude cambie con `Bash` o `PowerShell` no pasa por esas herramientas y no se ve. `npm test` de este proyecto usa la misma escalera.
- **«You should know».** Es el plugin integrado `cc-plugin-you-should-know@builtin`, apagado de serie en Claude Code. ClaudHome lo enciende con `enabledPlugins` en los `--settings` de cada sesión, que se suman a los del usuario sin pisarlos. Si tu `~/.claude/settings.json` ya dice algo de ese plugin, no se toca.
- **Animación de arranque.** `src/renderer/splash.js` dibuja la escena sobre una capa (`#splash`) que está en el HTML desde el principio, así que lo primero que se pinta es la animación y no la interfaz. La escena va en un escenario de 1280 × 800 escalado a la ventana, y todo se mueve con la Web Animations API desde un mismo reloj. Al final, la carpeta y el nombre se encogen hasta la posición real del icono y del nombre de la cabecera (medidas con `getBoundingClientRect`). El trazo pasa de 4 a 30 unidades para acabar con el mismo grosor que el icono. Las pestañas que vuelan son copias de las reales, hechas justo antes de salir; las reales, el icono y el nombre se esconden (`.splash-landing`) hasta que llegan sus copias. Para pruebas, `CLAUDES_NO_SPLASH` la quita y, desde el código, `CLAUDES_SPLASH_AT=<ms>` la deja quieta en ese instante.
- **Sesiones dormidas.** La interfaz revisa cada minuto las pestañas que no se ven. Si la sesión está en «Activa, esperando tu mensaje» y lleva 45 minutos sin cambios de estado ni teclas, se termina su proceso, igual que al reiniciarla, y la pestaña queda como «Dormida». Al mostrarla arranca con `--resume`, como al abrir la app. Los hooks marcan si Claude ha dejado algo en marcha: herramientas con `run_in_background` (comandos o agentes), `Monitor`, `CronCreate` o `ScheduleWakeup`. En ese caso, esa sesión no se duerme hasta que se reinicie.
- **Log.** `src/main/netlog.js` se alimenta del hook `PostToolUse`, es decir, de las herramientas que ya se han ejecutado: `Read`, `Grep`, `Bash`/`PowerShell`, `WebFetch`, `WebSearch` y las de los servidores MCP. El tamaño del aviso del hook da una idea de cuánto recibió Claude. De los avisos de más de 64 KB solo se lee el principio, y de ahí se sacan la herramienta y su entrada (`hooks.js`). Se considera que sale «hacia internet» lo siguiente:
  - las páginas y búsquedas web;
  - los MCP remotos (los conectores de claude.ai y los servidores con URL pública en `~/.claude.json` o `.mcp.json`);
  - los comandos con red cuyo destino no es la red local.
  
  Los secretos se tapan antes de mostrar o guardar nada. Las repeticiones del mismo elemento se agrupan durante 5 minutos. El archivo es `logs\salidas-<fecha>.log`.
- **Vista previa.** La terminal busca en cada línea rutas absolutas de Windows, con o sin comillas, incluidas las que Claude Code parte en dos líneas. Solo se marcan las que existen como archivo (`src/main/preview.js`). Claude Code numera las imágenes pegadas (`[Image #1]`, `[Image #2]`…) sin repetir número durante la sesión. Al pegar, la app mira qué etiqueta nueva aparece en pantalla y la asocia al archivo pegado; si Claude se reinicia, esa asociación se olvida. Las miniaturas de imágenes las da Windows (`nativeImage.createThumbnailFromPath`). La primera página de un PDF la dibuja el lector de PDF de Windows (`Windows.Data.Pdf`, en `src/main/pdf-page.ps1`), lanzado como comando codificado para no depender de la política de ejecución de scripts.
- **Datos.** `%APPDATA%\Claudes\state.json` guarda pestañas, recientes, posición de la ventana y si las imágenes con Codex y el micrófono para dictar están activados.

La interfaz usa módulos nativos del navegador (`<script type="module">`), sin empaquetador: cada archivo de `ui/` exporta lo que usan los demás e importa lo que necesita. El estado compartido está en `ui/state.js`; una variable importada no se puede reasignar desde otro módulo, así que las que cambian desde fuera tienen su función `setX` junto a su definición.

## Desarrollo

```
npm start          # abrir la app desde el código
npm test           # revisión del código, ESLint y pruebas automáticas
npm run lint       # solo ESLint
npm run icon       # regenerar build/icon.ico
npm run package    # generar dist/Claudes-win32-x64
```

`npm test` no arranca la app. Hace tres cosas, y si una falla no sigue. Primero pasa `scripts/check.mjs`, que revisa la sintaxis de todos los archivos y la coherencia entre las tres partes de la app: que cada `#id` que usa la interfaz exista en `index.html`, que cada `api.x()` exista en `preload.js`, que cada canal tenga quien lo atienda en el proceso principal y que la versión tenga su sección en `CHANGELOG.md`. También comprueba que lo que cada módulo de la interfaz importa exista y esté exportado en el otro (si no, la ventana se queda en blanco). Además avisa, sin fallar, de los archivos que crecen: cuando uno llega a 1 000 líneas y cada vez que aumenta un 20 % más (1 200, 1 440, 1 728…) toca revisar si conviene partirlo. Tras revisarlo, se parta o no, se anota con `npm run revisado -- <archivo> "motivo"` y el aviso calla hasta el siguiente escalón (lo anotado queda en `scripts/revisiones-tamano.json`). Después pasa ESLint (`eslint.config.mjs`), que entiende el código de verdad: avisa de nombres usados sin definir o sin importar, de variables e imports que ya no se usan y de otros descuidos, con un entorno distinto para el proceso principal (Node) y para la interfaz (navegador y módulos). Por último ejecuta las pruebas de `test/`, que cubren los módulos del proceso principal (hooks, contexto, límites y tokens, «Log», conversaciones, MCP, guardado, pestañas, estilo de las respuestas, procesos de terminal) y la actualización completa contra un servidor local, incluido el instalador. GitHub las ejecuta en cada subida.

Al ejecutar desde el código, `window.claudesTest` ofrece ayudas para las pruebas de la interfaz. Una de ellas, `benchTerminal(megas)`, vuelca salida de prueba en la terminal de la pestaña activa y devuelve lo que tarda en procesarla y a cuántos fotogramas se pinta. Con el dibujo actual de xterm (DOM) son unos 50 MB/s a unos 60 fotogramas por segundo, por eso no se usa el complemento WebGL.

Para probar sin tocar tus pestañas reales, estas variables solo actúan al ejecutar desde el código:

| Variable | Efecto |
| --- | --- |
| `CLAUDES_USER_DATA` | Carpeta de datos alternativa (también funciona en el ejecutable) |
| `CLAUDES_SHOT` | Guarda una captura de la ventana en esa ruta (`CLAUDES_SHOT_DELAY` en ms, `CLAUDES_SHOT_QUIT=1` para cerrar después) |
| `CLAUDES_TEST_JS` | Ejecuta ese archivo en la interfaz antes de la captura |
| `CLAUDES_AUTO_CONFIRM` | Acepta solos los diálogos (elige siempre el primer botón) |
| `CLAUDES_BLOCK_PROMPTS` | Los mensajes se rechazan antes de llegar al modelo: permite probar sin gastar tokens |
| `CLAUDES_LOG_HOOKS` | Escribe en la consola los avisos de hooks y las peticiones MCP |
| `CLAUDES_UPDATE_FAKE_VERSION` | Finge que la versión instalada es esa, para que aparezca el botón «Actualizar» (también funciona en el ejecutable) |
| `CLAUDES_UPDATE_AUTO` | Actualiza sin preguntar en cuanto hay versión nueva, y reinicia al terminar (para pruebas con el ejecutable) |
| `CLAUDES_UPDATE_URL` | Dirección de la que se descargan las versiones, en vez de los releases de GitHub (también funciona en el ejecutable) |
| `CLAUDES_DESKTOP_DIR` | Carpeta donde se comprueba el acceso directo en vez del escritorio |
| `CLAUDES_SLEEP_MINUTES` | Minutos sin actividad tras los que se duerme una sesión que no se ve (45 si no se indica; admite decimales para probar) |

Con `CLAUDES_USER_DATA`, la actualización trabaja en `<datos>\actualizacion` en vez de en `%LOCALAPPDATA%\Claudes-update`.

## Publicar una versión

Al subir a `main`, GitHub Actions (`.github/workflows/ci.yml`) pasa las pruebas y, si la `version` de `package.json` todavía no tiene release, genera el ejecutable en un Windows limpio, lo comprime y lo publica como release `vX.Y.Z` junto con su `latest.json` (`scripts/release.mjs`). Tarda unos minutos; hasta que termina, las instalaciones siguen viendo la versión anterior. Si las pruebas fallan, no se publica nada. Las instalaciones detectan la versión nueva cuando ese release es mayor que la suya, y antes de pulsar «Update» enseñan lo que trae cada versión según `CHANGELOG.md`. Para publicar una:

1. Añade arriba de `CHANGELOG.md` su sección: `## X.Y.Z — AAAA-MM-DD` y un punto (`- `) por cambio, escrito para quien usa la app.
2. Sube la versión y publícala:

```
npm version 0.6.0 --no-git-tag-version
git commit -am "ClaudHome 0.6.0: …"
git push origin main
```

Una versión anterior a la 0.2.0 no tiene actualizador: se actualiza a mano una vez (`npm run package` con ClaudHome cerrado).
